# F2 企业知识库 — Clarifications

> 本文件记录 `specs/F2-knowledge-base.md` §7 开放问题的最终决策，plan/tasks/implement 阶段以本文件为准。
> 决策不修改 spec 原文；与原文存在细化/覆盖关系时逐条注明。

## Clarifications

- Q1: 中文分词方案与初始标签体系 → 决策：分词采用 PostgreSQL 内 zhparser 扩展，并随附工程自定义词典（词典文件作为部署产物随包交付，词表由 AI 管理员可维护；F3.1.3 的 tsvector 关键词通道复用同一分词配置，保证 F2 搜索与 RAG 召回一致）；标签不预置固定标签集，Phase 1 提供空初始集，允许有权限用户自由创建标签，搜索筛选页提供"常用标签"聚合（按使用频次）辅助输入（理由：zhparser 为纯本地 PG 扩展，满足 FR2.6.2 私有化"外呼=空"且零额外服务；预置标签集在 Phase 1 无业务输入，自由打标 + 频次聚合实现成本最低；影响 FR2.4.1、FR2.6.2，并细化 FR2.2 的"分类固定、标签自由"边界）。
- Q2: 被引用文档是否允许删除 → 决策：允许删除但仅为软删除，且采用"删除 = 同时下架"双层语义：删除前必须展示引用方列表（FMEA/报告/RAG 引用链）并二次确认；软删除后文档即下架——不再参与全文检索（FR2.4）、AI 推荐（FR2.5）与 RAG ingestion/召回（FR3.1，chunk 标记下架），但对象详情、版本历史与既有引用记录完整保留以满足审计追溯；任何角色均无物理删除入口，物理清除仅限管理员后台数据保留策略（Phase 1 非目标，不实现）（理由：PRD §44/F10 要求全程可追溯，物理删除会破坏引用链与 kb_version 一致性，而下架已满足"不再误导检索"的真实诉求；影响 FR2.1.5、FR2.4.3、FR2.5.2，细化 FR2.1.5 的删除语义）。
- Q3: 相同 SHA-256 是否共享物理文件 → 决策：是。MinIO 采用内容寻址存储（对象 key = `sha256/<hash>`），多个 `document_version` 逻辑引用同一物理对象；入库去重（FR2.1.2）的"仍作为新关联上传"仅新建 document/document_version 逻辑记录，不复制文件（理由：零成本实现引用完整性，节省存储且天然保证版本内容不可变；影响 FR2.1.2、§3 数据模型 `document_version.file_key`）。
- Q4: 历史版本是否参与 RAG 检索 → 决策：否，仅文档最新版本（current_version）的 chunk 参与检索；新版本生效时旧版本 chunk 置 `superseded=true`（对齐 F3.1.2 与 F3 Q2 的默认"否"），`kb_revision` 记录每次切换；历史版本仍可通过文档详情页人工查看（AC2.1.1），未来如需"主动检索历史版本"作为 F3 的可配置项另行立项（理由：新旧版本同库混合召回会显著拉低引用准确率（AC3.2.1），默认排除是检索质量的正确取舍，且 F3 侧已按此默认设计；影响 FR2.5.2、§3 `kb_revision`，与 F3 Q2 决策保持一致）。

## Assumptions

- zhparser 自定义词典的维护入口挂在 F10 的 AI管理员角色下（与分类树管理同权限），Phase 1 仅提供词典文件替换 + 重载方式，不做在线编辑 UI。
- "常用标签"聚合基于 `document_tag` 使用频次的只读统计，不引入额外配置表。
- 引用方列表的数据来源为 F3.4.2/F7.3 的 `object_source_link` 与 FMEA/报告对象的外键引用，实时查询，不做引用计数冗余字段。
