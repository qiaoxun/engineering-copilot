# F8 测试需求与用例生成 — Feature Spec

| | |
| ---- | ---- |
| 编号 | F8 |
| 来源 | PRD §46.7、§30–31；UI 页面19/20；PHASE1_FEATURES F8.1–F8.6 |

| 被依赖 | F9（用例+判定标准是报告输入）、F4（testcase_gen 技能） |
| 里程碑 | M4 |

## 1. 概述

从规格书、客户需求、企业测试标准、历史用例生成测试需求（PRD §30 七要素）与测试用例（PRD §31 七字段）；区分新增/复用并统计；逐条人工处置；项目内用例库管理执行状态。验收 KPI：测试需求覆盖率可统计。

## 2. Feature Units

### F8.1 输入资料勾选

- **FR8.1.1** 生成入口提供四类资料勾选：规格书 / 客户需求 / 企业测试标准 / 历史用例（均来自当前项目关联文档与历史用例库，UI 页面20）。
- **FR8.1.2** 每类可多选、可跨类组合；至少选择 1 项方可发起生成。
- **FR8.1.3** 已选清单在生成配置页常显；历史用例支持按项目/关键词筛选选择。

### F8.2 测试需求输出

- **FR8.2.1** 输出字段（PRD §30 七要素）：`测试项目 / 测试目的 / 测试条件 / 测试方法 / 测试设备 / 样本数量 / 判定标准`；结构化存储，字段任一为空即该条无效（生成侧自检）。
- **FR8.2.2** 每条需求附依据引用：来自所选输入的具体文档片段（复用 `object_source_link`）。
- **FR8.2.3** 输出为 [AI] 草稿，逐条处置（F8.5）后才进入有效需求集。

### F8.3 测试用例输出

- **FR8.3.1** 输出字段（PRD §31）：`Case ID / 前置条件 / 输入条件 / 操作步骤（编号列表）/ 预期结果 / 判定标准 / 测试设备`。
- **FR8.3.2** Case ID 自动生成：`TC-{项目代号}-{序号}`，生成时预占号段避免冲突。
- **FR8.3.3** 每条用例必须挂到 ≥1 条测试需求（覆盖率统计基础）；无法挂接的用例标注"未映射需求"并计入统计。
- **FR8.3.4** 判定标准尽量携带量化阈值（来自规格书参数字段，可定位原文）。

### F8.4 生成统计（新增/复用）

- **FR8.4.1** 复用判定：生成结果与历史用例库匹配（用例语义相似度 ≥ 阈值）→ 标记"复用"并给出来源用例链接；其余标记"新增"。
- **FR8.4.2** 生成完成输出统计卡：`新增 N 条 / 复用 N 条`，复用项可展开看历史来源。
- **AC8.4.1** 对已有历史用例的重复项目发起生成，统计卡正确区分新增/复用（金标场景）。

### F8.5 逐条处置

- **FR8.5.1** 每条需求/用例可：`采用 / 编辑后采用 / 查看依据`；查看依据侧滑展示来源文档片段并跳原文。
- **FR8.5.2** 编辑记录前后 diff（审计 + 修改率统计）；采用后进入项目有效需求/用例集。
- **FR8.5.3** 支持批量采用/忽略（按筛选条件）。

### F8.6 用例库管理

- **FR8.6.1** 项目内用例集视图：列表 + 执行状态 `未开始 / 进行中 / 通过 / 失败`；状态流转记录操作人与时间。
- **FR8.6.2** 状态为人工更新（Phase 1 不接自动化测试系统），支持批量导入状态更新（Excel）。
- **FR8.6.3** 项目结项（或手动操作）后用例进入"历史用例库"，供 F8.1.3/F8.4 复用。
- **AC8.6.1** 用例状态变更后在列表与详情同步可见，历史可查。

## 3. 数据模型（核心）

| 实体 | 关键字段 |
| ---- | ---- |
| `test_requirement` | id, project_id, fields(7要素), source_links[], status(draft/adopted/ignored), ai_generated, created_by |
| `test_case` | id, case_no(TC-xxx), requirement_ids[], precondition, input, steps[], expected, criteria, equipment, reuse_of?(历史用例id), status(draft/adopted), exec_status(未开始/进行中/通过/失败) |
| `historical_case` | test_case 的归档视图（来源项目、时间） |
| `generation_run` | id, project_id, inputs[], stats{new, reused}, status —— 供审计与统计 |

## 4. API 概要

```
POST /api/v1/test-gen/runs                  # 发起生成（异步，勾选inputs）
GET  /api/v1/test-gen/runs/{id}             # 统计+结果列表
POST /api/v1/test-requirements/{id}/dispose # 采用/忽略
POST /api/v1/test-cases/{id}/dispose
PATCH /api/v1/test-cases/{id}/exec-status   # 执行状态更新
GET  /api/v1/projects/{id}/test-coverage    # 覆盖率统计
POST /api/v1/projects/{id}/cases/archive    # 归档入历史用例库
```

## 5. 横切接入（F10）

- **状态机**：需求/用例 `DRAFT →（人工处置）→ ADOPTED/IGNORED`；执行状态独立于 AI 状态机。
- **审计**：`testgen.run`（模型/prompt版本/kb_version/输入清单/输出数）、`case.edited`（diff）、`case.adopted/ignored`、`case.exec_status.changed`。
- **KPI**：`testgen.start → dispose完成` 耗时；需求覆盖率报表：`覆盖率 = 有≥1条已采用用例的需求 / 已采用需求总数`（口径见 Q3）。

## 6. 非目标

自动化测试脚本生成、测试执行调度、与 TCM/试验管理系统对接（第二阶段及以后）。

## 7. 开放问题

- **Q1** 企业测试标准文档的形态（结构化标准 vs 扫描件），决定复用率与抽取难度，需尽早拿到样例。
- **Q2** 复用判定相似度阈值初值与复用误判（误复用）的兜底提示方式。
- **Q3** 覆盖率口径需与质量部对齐（是否按需求类型加权）。
- **Q4** Case ID 号段规则是否需要与企业既有编号体系兼容。
